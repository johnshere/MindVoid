# 思无涯 (MindVoid) — 技术架构设计

## 1. 概述

思无涯 (MindVoid) 是一个**预测输入的外挂界面**，核心设计原则：

| 原则         | 含义                                     |
| ------------ | ---------------------------------------- |
| **不侵入**   | 不替换、不劫持现有输入法，仅平行叠加     |
| **低延迟**   | 击键到预测展示目标 < 10ms（学习参考，非硬性标准）    |
| **离线优先** | 训练与推理均在本地完成，隐私不泄露       |
| **自演进**   | 每位用户得到独一无二、持续进化的预测模型 |

---

## 3. 用户界面层

面向用户的部分：浮窗渲染、交互响应、配置管理。不涉及输入捕获和模型逻辑。

---

### 3.1 浮窗渲染

**浮窗渲染方案：**

| 方案                                       | 优势                   | 劣势                 | 推荐场景   |
| ------------------------------------------ | ---------------------- | -------------------- | ---------- |
| **平台原生** (Win32 HWND / macOS NSWindow) | 最低延迟, 系统整合最好 | 跨平台代码不共享     | 生产首选   |
| **Skia 直接渲染** (无窗口管理器)           | 跨平台统一渲染         | 需处理窗口合成       | 备用方案   |
| **Tauri / WebView**                        | 开发速度快, UI 灵活    | 延迟略高 (~5ms 额外) | 原型 / MVP |

**浮窗行为：**

- 始终置顶、无焦点、点击穿透（仅特定区域可交互）
- 跟随光标位置，超出屏幕边缘时自动翻转
- 半透明毛玻璃效果 (Acrylic / Vibrancy / Blur)
- 候选列表：最多 5 项，支持鼠标点击选词或全局组合键（如 `Alt+1~5` / `Ctrl+Shift+1~5`，可自定义）

---

### 3.2 交互流程

> ⚠️ **已知风险：推理排队与延迟堆积**
> 高频率打字时，每次击键都触发推理。若推理耗时 > 击键间隔，将出现「永远在取消、永远无结果」的排队堆积。
> **缓解方向：** 引入击键去抖（用户停顿 >50ms 才触发推理）+ 推理队列优先级标记（详见 §9）。

```
用户打字 → 适配层捕获 → 过滤 → 判定修正 → 缓冲区 → 目标池切换/激活 → [去抖 50ms] → 引擎预测 → UI 展示候选
                                                                               │
                                   用户鼠标点击/组合键选词 ───────────────────┤
                                   用户继续打字 ───────────────────────────────┘
                                        │
                                   推理-训练一体回路
                                  ┌─────────────────┐
                                  │  兜底方案: N-Gram 即时计数更新  ← 每次击键
                                  │  自研模型: 待后期设计实现       ← 学习研究
                                  │  闲时: 后台巩固               ← 闲置后台
                                  └─────────────────┘
```

### 4.2 多设备输入适配抽象层

将所有输入源统一为标准化事件接口，隔离底层差异。上层只需消费标准化事件，无需关心底层平台 API 细节。

```

【多设备输入源】
├── 键盘 (主要) → 标准化为"键盘增量字符事件"
├── 剪贴板 (辅助) → 标准化为"文本粘贴事件"
├── 语音 (预留) → 标准化为"语音转录事件"
└── 手写 (预留) → 标准化为"手写识别事件"
↓
【硬件输入适配抽象层】
类型标注 · 源路由 · 统一事件接口
↓
送入敏感过滤 (§4.5) → 分支 1
（输入框文本变化事件经 UI 适配层 → 敏感过滤 → 分支 2，见 §4.1 全貌图）

```

每种输入源实现统一的适配接口（轮询事件、标记来源），上层无需关心底层差异。

#### 4.2.1 键盘增量字符捕获

低层级键盘钩子，仅监听不拦截。捕获的原始按键序列以标准化字符事件形式产出，经公共敏感过滤拦截层 (§4.5) 后作为分支 1 送入判定器 (§4.7)，与环境文本（分支 2，同样经敏感过滤）比对后决策缓冲操作。

> ⚠️ **已知风险：三方输入冲突**
> 键盘钩子捕获的是原始按键序列，**不是最终落地的文本**。用户通过 IME 解码、候选选择、拼音回退等操作产生的中间按键会被一并捕获，导致预测上下文与编辑器实际内容不一致。
> **当前缓解：** 编辑行为判别器（§4.7）通过比对环境文本来修正缓冲区，在分支 1 内完成校准。

| 平台            | 方案                                                | 延迟  |
| --------------- | --------------------------------------------------- | ----- |
| Windows         | `SetWindowsHookEx(WH_KEYBOARD_LL)` — 低层级键盘钩子 | < 1ms |
| macOS           | `CGEventTap` + `AXObserver` (辅助功能权限)          | < 1ms |
| Linux (X11)     | `XRecordExtension` 或 `libxkbcommon`                | < 2ms |
| Linux (Wayland) | 虚拟键盘协议 `zwp_input_method_v2`                  | < 2ms |

**处理流程：**

```

原始按键事件 → 按键序列组合 → 字符解码 → 标准化字符事件
↓ ↓
原始 IME (透传) 送入敏感过滤 (§4.5) [分支 1]

```

**增量特性：** 每次只传递新输入的**字符增量**（而非整个输入），减少下游处理负担。

**数据流向（分支 1）：** `键盘钩子 → 敏感过滤 (§4.5) → 判定器 (§4.7) → 环形缓冲区 (§4.8)`。分支 2 数据流见 §4.6。编辑行为判定逻辑见 §4.7。

整体数据流见 §4.1 核心层全貌图。

### 4.3 UI 适配层

跨平台统一接口，负责**光标上下文获取**和 **targetId 生成**，不处理击键事件。

```
【UI 适配层】
  ├── get_active_target_id() → 当前输入目标唯一标识
  ├── get_cursor_prefix/suffix() → 光标前后文本
  ├── get_cursor_position() → 光标屏幕坐标
  └── on_focus_changed() → 焦点变化事件流
```

targetId 由三平台各自实现，外部统一消费：

| 平台        | 方案                                       | 跨应用          |
| ----------- | ------------------------------------------ | --------------- |
| **Windows** | UIA RuntimeId 节点路径（平台原生）         | ✅ 是           |
| **Android** | AccessibilityNodeInfo 层次路径（平台原生） | ✅ 是           |
| **iOS**     | accessibilityIdentifier 链（平台原生）     | ⚠️ 仅本扩展进程 |

targetId 直接复用各平台辅助功能框架的节点标识，不自创 hash 规则：

- **Windows UIA:** `CreateCondition` + RuntimeId 数组已全局唯一
- **Android A11Y:** `getViewIdResourceName()` + 从根到叶的节点层次
- **iOS:** `accessibilityIdentifier` 结合容器路径

iOS 以 Keyboard Extension 运行时无法获取其他应用控件信息，光标上下文依赖 `UITextInput` 协议。该限制在后续产品化阶段评估。

UI 适配层的输出供给三个消费方：

- **TargetPool**（§4.4）— 依据 targetId 查/建/切目标上下文
- **环境采集模块**（§4.6）— 依据光标位置获取前后文本
- **浮窗渲染**（§3.1）— 获取光标屏幕坐标，定位浮窗

### 4.4 目标上下文管理池

传统做法在光标/焦点切换时清空缓冲区重新采集，导致频繁切换时上下文丢失、切回时状态归零。目标上下文管理池为每个输入目标保留独立状态解决此问题。

**TargetContext 核心字段：**

| 字段         | 说明                                                | 上限       |
| ------------ | --------------------------------------------------- | ---------- |
| targetId     | 唯一标识（由 UI 适配层 §4.3 生成）                  | 固定大小   |
| 击键缓冲区   | 环形滑动窗口实例（行为规范见 §4.8）                 | 512 字符   |
| 光标前文本   | 当前光标之前的文本内容                              | 1 KB       |
| 光标后文本   | 当前光标之后的文本内容                              | 1 KB       |
| 应用/窗口名  | 来源应用上下文                                      | ~100 bytes |
| 缓存候选列表 | 上次预测结果，用于快速短路                          | 5 项       |
| 最近激活时间 | 用于 LRU 淘汰排序                                   | 8 bytes    |

单目标 ~3.2 KB，池上限 16 个目标（~51 KB），LRU 淘汰。

> ⚠️ **隐私边界：** 跨应用切换时旧目标缓冲区保留，但切换到黑名单应用（如密码管理器）时强制清空旧目标缓冲区。非活跃目标缓冲区保留至 LRU 淘汰或隐私策略触发清空。

**核心操作：**

| 操作 | 行为                                                |
| ---- | --------------------------------------------------- |
| 查池 | 用 targetId 查询 → 存在则激活                       |
| 新建 | 不存在 → 创建 TargetContext，环境采集，初始化缓冲区 |
| 切换 | 终止旧目标的 pendingInferTask，激活新目标           |
| 淘汰 | 超 16 上限 → 丢弃 LRU（最久未激活）目标             |

**三种切换行为：**

| 场景                 | 行为                                                         |
| -------------------- | ------------------------------------------------------------ |
| 同目标光标移动       | 走场景 A（裁剪缓冲区，保留上下文）                           |
| 同应用不同输入框     | 保留旧目标上下文，新建/激活新目标                            |
| 跨应用焦点切换       | 保留旧目标上下文，但检查隐私策略——若新目标为黑名单应用，强制清空旧目标缓冲区 |

**场景 A — 同目标光标移动：**

```
光标位置变化
    ↓
UI 适配层重新获取 cursorPrefix / cursorSuffix
    ↓
更新当前 TargetContext 上下文
    ↓
裁剪环形缓冲区（丢弃光标后字符，保留光标前有效部分，见 §4.8）
    ↓
取消上一轮未完成推理 → 重新执行预测
```

**场景 B — 跨目标切换：**

```
光标切换 → UI 适配层计算新 targetId
    ↓
┌── TargetPool 中存在? ──┐
│  是 → 激活已有目标       │
│       ├ 光标位置未变 → 展示缓存候选
│       └ 光标位置变化 → 走场景 A
│  否 → 创建新 TargetContext
└────────┬────────────────┘
    ↓
终止旧目标 pendingInferTask → 新目标上下文送入预测
```

### 4.5 敏感过滤

作为公共拦截层，位于所有数据源（键盘增量 / 输入框文本变化事件）进入判定器之前。文本在进入环形缓冲区**之前**即被过滤，保证缓冲区中不残留敏感数据。

**过滤目标：**

| 类别                     | 判断依据                            | 处理方式               |
| ------------------------ | ----------------------------------- | ---------------------- |
| 密码输入                 | 焦点在密码框 (OS 属性 `IsPassword`) | 整段丢弃，不进入下游   |
| 银行卡号                 | 纯数字 14-19 位正则                 | 用 `[REDACTED]` 替换   |
| 连续数字 (手机号/身份证) | 11 位纯数字 / 18 位数字+X           | 用 `[REDACTED]` 替换   |
| 邮箱地址                 | 正则匹配                            | 替换为 `[EMAIL]`       |
| URL                      | 协议 + 域名正则                     | 替换为 `[URL]`         |

（过滤流程见 §4.1 核心层全貌图）

**设计要点：**

- 过滤在**内存中**完成，不写入磁盘
- 替换后的占位符保留句法位置（不影响上下文长度）
- 黑名单应用整段跳过（不进入缓冲区）

### 4.6 全局环境采集模块

| 属性     | 值                     |
| -------- | ---------------------- |
| **性质** | 可选增强               |
| **默认** | 开启                   |
| **允许** | 关闭（用户可随时禁用） |

**采集内容：**

| 数据项       | 来源         | 用途                            |
| ------------ | ------------ | ------------------------------- |
| 光标前文本   | 辅助功能 API | 参与判定器编辑比对，修正缓冲区  |
| 光标后文本   | 辅助功能 API | 判断用户是否在插入/修改         |
| 焦点窗口标题 | OS 窗口管理  | 推断场景（IDE / 聊天 / 浏览器） |
| 应用进程名   | OS 进程管理  | 白名单/黑名单过滤               |

**平台方案：**

| 平台    | 方案                                              |
| ------- | ------------------------------------------------- |
| Windows | `GetCaretPos()` + `UI Automation` / `IAccessible` |
| macOS   | `AXUIElementCopyAttributeValue`（辅助功能权限）   |
| Linux   | IM 协议或 `AccessX`，Wayland 下受限               |

**开关机制：**

```toml
# config.toml
[environment_capture]
enabled = true               # 默认开启
blocked_apps = ["*password*", "*bank*", "*vault*"]  # 黑名单应用跳过
```

**数据流向：** `输入框事件 → 敏感过滤（§4.5）→ 环境采集 → 判定器（§4.7，用于编辑比对）→ 环形缓冲区（§4.8）→ 句子分段器（§4.9）`。环境采集在判定阶段介入，不直接与分段器交互，避免二次拼接。

关闭时：分支 2 数据丢弃，判定器仅依赖分支 1 的键盘增量事件。

### 4.7 编辑行为判别器

负责比对分支 1（标准化字符事件）与分支 2（环境文本），判定用户执行的是增量输入还是编辑操作，并将修正后的文本写入环形缓冲区。判定器是连接两个输入分支的汇合决策点（见 §4.1 流程图节点 H）。

**输入与输出：**

```
分支1: 标准化字符事件流（已过滤）
分支2: 环境文本（光标前后，已过滤，可选）
            ↓
       差值比对
     （分支1 增量 vs 分支2 完整文本）
            ↓
   ┌────────┴────────┐
   ↓                 ↓
增量判定             编辑判定
   ↓                 ↓
精确短词 (I)        长句修正 (J)
   ↓                 ↓
   └────────┬────────┘
            ↓
   修正后文本 → 环形缓冲区 (§4.8)
```

**判定逻辑表：**

| 用户行为      | 分支1 原始信号 | 分支2 参考文本       | 判定 | 缓冲操作               |
| ------------- | -------------- | -------------------- | ---- | ---------------------- |
| 正常连续打字  | 字符序列       | 一致                 | 增量 | 尾部追加               |
| IME 候选选词  | 拼音+空格+数字 | 完整词               | 编辑 | 用环境文本替换缓冲尾部 |
| 退格删除      | 退格键         | 文本缩短             | 编辑 | 裁剪缓冲尾部           |
| 光标位置插入  | 字符序列       | 文本变长(带插入位置) | 编辑 | 在对应位置插入         |
| 批量删除/剪切 | 多个退格/无    | 文本大幅缩短/为空    | 编辑 | 清空或大幅裁剪         |
| 外部粘贴      | 无/修饰键      | 大段新文本           | 编辑 | 整段采纳环境文本       |

**增量 vs 编辑输出路径说明：**

| 路径      | 触发条件                   | 下游节点     | 含义                              |
| --------- | -------------------------- | ------------ | --------------------------------- |
| 精确短词  | 增量操作（尾部追加少量字符） | 缓冲区直接写入 | 输入内容可信任，无需大范围修正    |
| 长句修正  | 编辑操作（IME/退格/粘贴等） | 结合环境文本重写缓冲区 | 需要以环境文本为基准修正缓冲区内容 |

判定器输出的**已修正缓冲区**作为单一可信数据源送入下游句子分段器 (§4.9)，下游无需关心数据来源。

---

### 4.8 环形输入缓冲区

**容量：** 512 字符滑动窗口

> ⚠️ **已知风险：光标移动语义断裂**
> 纯字符缓冲区不携带光标相对位置信息。相同字符序列在句子开头 vs 中间 vs 末尾含义完全不同，单纯裁剪缓冲区无法对齐语义位置。
> **缓解方向：** 缓冲区引入光标位置标记（如特殊 token `<CURSOR>`），作为缓冲区的元数据字段（非字符内容），模型训练时将该标记作为输入特征，使预测引擎感知光标上下文偏移。

**与 TargetPool 的关系：** 每个 TargetContext（§4.4）持有一个独立的环形缓冲区实例。本节描述的是**单个缓冲区实例的行为规范**，§4.4 描述的是 **16 个实例的池化管理与生命周期**。

```
判定器输出 (已修正文本) (§4.7)
    ↓
环形缓冲区 char[512]
· 增量操作 → 尾部追加
· 编辑操作 → 按差值修正
    ↓
窗口指针指向最新写入位置
    ↓
提取上下文: buffer[(pos-context_len)..pos]
```

**行为规则：**

| 事件         | 行为                                                         |
| ------------ | ------------------------------------------------------------ |
| 输入字符     | 追加到缓冲区尾部，窗口前进                                   |
| 退格删除     | 移除缓冲区尾部，窗口回退                                     |
| 光标移动     | 裁剪光标后字符，保留光标前有效部分（配合 TargetPool 场景 A） |
| 活跃目标切换 | 挂起当前目标缓冲区，激活新目标缓冲区；旧目标缓冲区保留至 LRU 淘汰或隐私策略触发清空 |
| 缓冲区满     | 覆盖最旧字符（环形滑动）                                     |

---

### 4.9 句子分段

已修正且已过滤的缓冲区文本送入分段器。环境文本已在判定阶段（§4.7）介入并完成修正，分段器不再重复拼接。

```
已修正缓冲区（已过滤，已判定修正）
           ↓
     句子分段器
    · 标点分句（。！？；）
    · 长文本分片（> 256 字截断）
    · 去噪（重复空格/控制字符）
           ↓
      特征提取器 → 送入模型层 (§5)
```

---

### 4.10 特征提取器

连接核心层与模型层的桥梁。负责将分段后的文本转化为模型可消费的特征输入。

```
句子片段（纯文本，≤256 字）
        ↓
   特征提取器
   · N-Gram 切片（1~3 元前缀列表）
   · 前缀匹配键（Trie 索引 key）
   · 上下文窗口（光标前 N 字滑动窗口）
   · 场景标签（应用名 / 窗口标题）
        ↓
   特征向量 → 模型层 predict() 接口
```

**与模型层的契约：** 特征提取器的输出格式与 §5 模型层的 `ModelBackend::predict()` 入参严格对应。替换 NN 模型时，特征提取器可独立扩展维度，不影响上游分段器和缓冲区。

---

### 4.11 训练样本分流器

位于环形缓冲区之后，负责将用户行为转化为训练样本，分流至模型层的增量训练链路。

**触发条件：**

| 事件               | 动作                           |
| ------------------ | ------------------------------ |
| 断句完成（标点）   | 生成完整句子样本，标记正例     |
| 用户选择候选词     | 生成 `(上下文, 选中词)` 正样本 |
| 用户继续打字（忽略） | 确认当前候选未被选中，丢弃     |

**样本格式：**

```
(输入上下文: String, 实际输出: String, 置信度标记: Confidence)
  - 输入上下文: 光标前 N 字的特征切片
  - 实际输出:   用户选中的候选词 / 继续输入的实际字符
  - 置信度标记: high | low | implicit（隐式负样本见 §9.4）
```

**下游连接：** 样本写入本地训练语料 (§5 模型层 → 双缓冲训练机制)，触发增量训练线程。样本质量保障策略（延迟确认、负样本标记等）见 §9.4。

整体数据流见 §4.1 核心层全貌图。

## 5. 模型层

### 5.1 模型架构

**首期方案：传统统计模型兜底**

```
输入上下文
    │
    └──→ 统计模型（具体方案待定）
          ├ 快速候选: 基于历史统计的前 3~5 个词/字
          ├ 存储: 待定（如 Trie 树 / 哈希表 / BTreeMap 等）
          └ 在线更新: 每次用户选择后即时调整计数
                ↓
          融合排序器
          ├ 去重 + Top-K 截断
          └ 输出 3~5 个候选词
```

> ⚠️ **注意：** 上述为兜底方案接口描述。
> 具体实现（数据结构、N 值、分词策略等）是项目核心学习研究课题，**不预设方案**，留待后期实验确定。
> 模型层定义了统一接口 `ModelBackend` trait，确保兜底方案与自研方案可互换。

### 5.2 增量训练

> ⚠️ **已知风险：训练噪声与模型退化**
> 当前回路假设「用户选择的 = 正确样本」，但实际存在大量噪声：将就选择、全部删除后重打、误触选择、多步修正等。不加区分地全部喂入训练会导致模型退化。
> **缓解方向：** 引入延迟确认（持续打字 N 字后才确认有效）、隐式负样本（翻页/退格标记负例）、置信度加权（低置信度命中加大学习率），详见 §9。

```
用户选择候选词 / 继续打字
        ↓
   训练样本生成
   (输入片段 → 实际输出)
        ↓
┌──────────────────────┐
│   双缓冲训练机制       │
│                      │
│  Buffer A (热)        │  ← 实时累积新样本
│  ┌──────────────────┐ │
│  │ 当前会话样本       │ │  达阈值 → 触发小批量微调
│  └──────────────────┘ │
│  Buffer B (冷)        │  ← 持久化存储 + 周期合并
│  ┌──────────────────┐ │
│  │ 历史样本库          │ │  每日/每周全量重训
│  └──────────────────┘ │
└──────────────────────┘
```

**训练策略：**
| 策略 | 触发条件 | 耗时 |
|------|----------|------|
| 即时微调 | 每收集 50 条新样本 | ~100ms (后台线程) |
| 轻量增量 | 每 500 条样本 | ~1s |
| 全量重训 | 每日/手动触发 | ~30s–5min |

### 5.3 模型格式与存储

```
~/.mindvoid/
├── models/
│   ├── current/          ← 当前活跃模型
│   │   ├── ngram.model   ← 模型序列化文件
│   │   └── config.json
│   ├── snapshots/        ← 历史快照 (按日期)
│   └── base/             ← 初始 N-Gram 基座

└── config.toml           ← 配置文件
```

## 6. 关键技术决策

### 6.1 为什么选 Rust 作为主力语言？

| 需求           | Rust 的优势                                                          |
| -------------- | -------------------------------------------------------------------- |
| 低延迟 | 零 GC 暂停, 编译期优化, 直接控制内存布局（学习参考目标 < 10ms） |
| 跨平台         | 一套核心逻辑编译到 Windows/macOS/Linux                               |
| 系统级钩子     | FFI 无缝对接 C 系统 API                                              |
| 安全           | 内存安全保证, 钩子代码不会引发系统崩溃                               |
| ML 推理        | 首期 N-Gram 无需外部 ML 框架，预留 ModelBackend trait 供后期 NN 接入 |

### 6.2 为什么不直接劫持输入法 (IME)?

- 输入法 API 各异 (TSF/InputMethodKit/IBus)，维护成本高
- 劫持容易破坏用户原有习惯和输入法皮肤/功能
- 外挂模式更安全：挂了就挂了一键重启，不影响打字

### 6.3 隐私设计

- **全部本地计算** — 键盘事件、模型训练、用户画像均不出设备
- **敏感过滤** — 密码、银行卡号、身份证等在内存中即被过滤，不入库
- **应用黑名单** — 用户可指定哪些应用不被采集/训练
- **透明日志** — 用户可以随时查看和清空训练数据
- **纯本地存储** — 模型权重、训练语料、用户画像均不出设备

## 9. 已知风险与应对

### 9.1 三方输入冲突（IME 断层）

| 维度     | 内容                                                                                                                                                                                                         |
| -------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **风险** | 键盘钩子捕获原始按键序列，IME 解码过程（拼音组合、候选选择、回退修正）产生的中间按键与最终落地的文本不一致，导致预测上下文断层                                                                               |
| **影响** | 🔴 致命 — 预测准确性根基不稳                                                                                                                                                                                 |
| **缓解** | 从「按键钩子为主」迁移到「平台文本变化事件为主，按键钩子为辅」：Windows UIA TextChanged / Android TYPE_VIEW_TEXT_CHANGED / iOS UITextInput。按键钩子仅用于触发时机加速（如击键后立即预拉取），不用于文本内容 |
| **阶段** | Phase 2                                                                                                                                                                                                      |

### 9.2 光标移动语义断裂

| 维度     | 内容                                                                                                                       |
| -------- | -------------------------------------------------------------------------------------------------------------------------- |
| **风险** | 纯字符环形缓冲区不携带光标位置信息。相同字符序列在句子开头 vs 中间 vs 末尾语义完全不同，裁剪后预测结果与用户实际位置不匹配 |
| **影响** | 🟡 中 — 短句/频繁修改场景预测错乱                                                                                          |
| **缓解** | 缓冲区引入光标位置标记（如特殊 token `<CURSOR>`），NN 模型将其作为输入特征之一参与训练，感知光标相对上下文的偏移           |
| **阶段** | Phase 2                                                                                                                    |

### 9.3 推理排队与延迟堆积

| 维度     | 内容                                                                                                                                                                                     |
| -------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **风险** | 每次击键触发推理，若推理耗时 > 击键间隔，新任务不断取消旧任务，导致计算资源浪费在取消/重跑上，最终无有效结果展示                                                                         |
| **影响** | 🟡 中 — 快速连续打字时体验下降                                                                                                                                                           |
| **缓解** | **击键去抖：** 用户停顿 >50ms 后才触发推理，期间持续击键则重置计时器。**队列优先级：** 新任务标记高优先级，低优先级任务执行完不展示。**时间预算：** 每次推理硬上限 5ms，超时返回部分结果 |
| **阶段** | Phase 1                                                                                                                                                                                  |

### 9.4 训练样本噪声与模型退化

| 维度     | 内容                                                                                                                                                                                                                                                                                               |
| -------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **风险** | 自训练回路假定「用户选择 = 正样本」，但存在将就选择、误触、全部删除后重打、多步修正等噪声。不加区分地全量喂入训练，模型逐步退化                                                                                                                                                                    |
| **影响** | 🔴 致命 — 长期自训练后准确率不升反降                                                                                                                                                                                                                                                               |
| **缓解** | **延迟确认：** 用户选词后持续打字 >5 字才确认样本有效，期间退格则丢弃。**隐式负样本：** 用户翻页查看后续候选项 → 当前 Top-1 标记隐式负例。**置信度加权：** 模型高置信度但用户未选 → 降低学习率；低置信度但用户选了 → 提高学习率。**定期回滚：** 保留校验集，检测到准确率下降时回滚到上一个稳定快照 |
| **阶段** | Phase 2                                                                                                                                                                                                                                                                                            |

### 9.5 targetId 现成方案可复用

| 维度     | 内容                                                                                                                     |
| -------- | ------------------------------------------------------------------------------------------------------------------------ |
| **风险** | 不自创 targetId 规则，直接复用平台辅助功能框架的节点标识路径                                                             |
| **影响** | 🟢 低 — 反而更稳定                                                                                                       |
| **缓解** | Windows 用 UIA RuntimeId、Android 用 AccessibilityNodeInfo 路径、iOS 用 accessibilityIdentifier 链。不需要自创 hash 规则 |
| **阶段** | Phase 1                                                                                                                  |
